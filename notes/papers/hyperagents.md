> **一句话总结：** Hyperagents 把“执行任务的 agent”和“修改 agent 的 meta agent”放进同一个可编辑程序，让系统既能改进解题方法，也能修改改进方法；最值得借鉴的是用 **improvement@k** 单独检验改进能力，而不是把任务分数上涨直接叫作递归自我改进。

## 一、论文概览：为什么先读这一篇

### 1. 基本信息与阅读范围

- **原题：** Hyperagents。
- **作者：** Jenny Zhang、Bingchen Zhao、Wannan Yang、Jakob Foerster、Jeff Clune、Minqi Jiang、Sam Devlin、Tatiana Shavrina。
- **状态：** 本文按 arXiv 预印本记录，不将其标注为已被 ICLR 或其他会议接收。
- **版本：** 本笔记依据 `arXiv:2603.19461v1` 的 60 页 PDF。arXiv 首次提交日期为 2026 年 3 月 19 日；下载的 PDF 首页标注 March 23, 2026。不同展示渠道的日期不混用，正文与图表以这一 PDF 为准。
- **材料：** 主文、附录与[官方代码仓库](https://github.com/facebookresearch/HyperAgents)。下面的实验数字均为论文报告，尚未独立复现。

选择它不是因为它已经解决了 RSI，而是它恰好连接了三个容易混淆的问题：

1. 一个 agent 能否把当前任务做得更好？
2. 它学到的东西能否帮助解决新任务？
3. **负责产生这些改进的方法，是否也变得更有效？**

对一个从技能库演化出发、还不知道怎样设计 RSI 实验的项目来说，第三个问题比“让系统多跑几轮”重要得多。这篇论文提供了可拆解的实现，也提供了可讨论的量化方法和并不完美的实验证据。

**建议阅读顺序：** 先看 Figure 1 理解修改对象，再读 §5.2 与 Appendix D.3 理解 `imp@k`，最后用 §5.3 和 §7 检查作者的主张到哪里为止。不必一开始逐行读完全部代码附录。

### 2. 先区分几个概念

**Task agent（任务 agent）** 接收任务输入并产出答案，例如代码补丁、论文录用预测、奖励函数或数学解答评分。

**Meta agent（改进器）** 接收程序、历史评估与日志，修改 task agent，也可以修改自身。这里的“meta”指操作层次，不代表它一定使用了某一种元学习训练算法。

**Hyperagent** 是两者组成的、可被自身修改的完整程序。可以记成：

$$
H = (A, M)
$$

其中 $A$ 负责做题，$M$ 负责产生程序修改。普通任务优化主要改变 $A$；本文要让 $M$ 也成为可改对象。

**Recursive Self-Improvement，RSI（递归自我改进）** 在不同工作中有不同的操作性定义。就本篇的理解而言，关键不只是反复修改程序，而是改进机制能够修改自身，且这种变化有机会提高后续改进能力。**递归结构存在、改进能力提高、长期持续加速，是三个不同强度的命题。**

**这里并没有更新基础模型权重。** 被演化的是程序、提示、工具使用流程和记忆等。机器人实验虽然调用强化学习来训练控制策略，但那是评估生成奖励函数的内层过程，不等于给 hyperagent 的基础模型做 RL 训练。

## 二、Motivation：为什么任务进步还不够

### 1. 固定改进器也能让任务分数上涨

设想一个固定流程：读取失败样例，提出补丁，运行测试，保留更好的版本。即使流程本身一字未改，只要搜索足够多次，也可能找到更好的程序。

因此，“第 100 轮比第 1 轮强”至少有几种解释：探索次数增加、积累了任务知识、找到更好的解题程序，或者真的学到了更有效的改进策略。只观察最终任务分数，无法把这些解释分开。

放在技能库场景中也是如此：**技能条目更多、某个 kernel 更快，并不自动说明负责编辑技能的系统更会改进了。**

### 2. 从 Darwin Gödel Machine 到 Hyperagents

论文建立在 Darwin Gödel Machine（DGM）上。DGM 通过修改代码和维护候选档案，搜索更强的 coding agent。在编程领域，“完成编程任务”和“修改自己的实现”都需要编程能力，两种能力存在天然重叠。

但这种重叠不一定延伸到其他领域。一个擅长预测论文录用的程序，未必擅长设计自身下一轮的修改；一个能生成机器人奖励函数的程序，也未必能从历史实验中学到更有效的搜索策略。

此外，原始 DGM 中分析日志、生成改进指令的一部分机制由人工固定。它会指导系统改代码，但**“怎样生成这些指导”本身没有同等程度地进入搜索空间**。

Hyperagents 的核心观察是：应该显式区分 task agent 与 meta agent，并让两者都可被修改。由此得到 DGM-Hyperagents，简称 **DGM-H**。

## 三、Method：把改进器也放进可编辑程序

### 1. 系统总览

Figure 1 最值得看的不是循环箭头，而是上下两部分绿色模块的差别：上方 DGM 保留了固定的手工指令生成机制；下方 DGM-H 由可演化的 meta agent 决定如何改写 hyperagent。

![Hyperagents 与原始 DGM 的对比：任务 agent 和 meta agent 共同进入自修改循环，并由外部任务评价筛选](./img/hyperagents-fig01-overview.png)

*图 1：DGM 与 DGM-H 的方法对比。下半部分将任务求解和自修改分开，不再要求两者天然是同一种能力。来源：原论文 Figure 1，PDF 第 4 页，CC BY 4.0；从原 PDF 裁切，未改动图中内容。*

可以把一轮演化概括为：

1. **选择父代。** 从历史档案中挑选一个 hyperagent，而不只使用当前最高分版本。
2. **提出并实施修改。** 父代的 meta agent 读取代码、过往评估和剩余预算，使用文件编辑、bash 等工具修改程序。
3. **形成子代。** 新版本可能改变 task agent、meta agent，或两者一起改变。
4. **评估任务能力。** 运行新版本的 task agent，获得外部任务分数。
5. **加入档案。** 符合运行与编译要求的候选进入档案，成为后续可能的父代。

这里很容易忽略一个设计：**演化时主要依靠任务表现来筛选，改进能力不是每一轮都由 `imp@k` 直接评分。** §5.2 的 `imp@k` 是后续诊断实验，用来检验搜索过程中是否产生了更好的改进器。

### 2. 为什么需要 archive，而不是只保留赢家

一个候选当前任务分数不最高，但它形成的错误分析、工具或记忆机制可能对后续有用。如果每轮只留下即时赢家，这些“垫脚石”可能被删掉。

DGM-H 因而保留历史候选的档案，综合任务得分和探索程度挑选父代。Appendix A.2 的父代选择倾向于高分、同时还没有产生太多子代的版本：表现好的版本值得利用，较少探索的版本也应得到机会。

这解释了论文中的 **open-ended exploration**：搜索不是一条不断覆盖旧版本的单链。不过，“保留多样候选”不等于已经证明了开放世界中的无上限进步。

### 3. 到底哪些部分能改，哪些不能改

主实验中，hyperagent 可以修改任务程序与自身改进机制；**外层父代选择与评估协议仍然固定**。附录另有允许修改父代选择机制的初步实验，不能据此把主结果描述成“整个系统的一切规则都能自由修改”。

这也提供了一个重要实验边界：让系统有能力改进实现，并不意味着让它修改测试答案、验收标准或最终计分器。论文在受限沙箱中执行生成代码，并设置资源和网络限制。

### 4. 它实际演化出了什么

论文的定性分析包括：从笼统的角色提示转向多阶段决策流程；记录性能变化；维护失败原因、过度修正与策略经验；在机器人任务中积累环境变量和奖励尺度知识。

这些例子有助于理解“改进器变了”是什么样，但还不是每项机制的因果证明。看到持久记忆与高分同时出现，不能直接推出“持久记忆造成了全部收益”；还需要有针对性的移除、交换或冻结实验。

## 四、Evaluation：先看它怎样证明任务变强

### 1. 四种任务分别测什么

**编程：Polyglot。** 输入仓库和自然语言需求，输出代码补丁，以测试是否通过计算 pass@1。附录列出 60 个训练任务，采用先 10 个、再另外 50 个的分阶段评估，没有单独验证集。

**论文评审。** 输入论文文本，预测 accept/reject；训练、验证、测试各 100 个任务。标签来自 ICLR 2024/2025、NeurIPS 2023/2024 的实际录用决定。指标是预测这些决定的准确率，**不是对“论文客观质量”的直接测量**。

**机器人奖励设计。** agent 生成奖励函数，然后在模拟器中用 RL 训练四足机器人。训练任务是向前行走，测试任务是最大化躯干高度，跳跃是有用策略。指标是训练后策略的任务分数，不是分类准确率。表中训练/测试的“6”代表重复实验次数，不是六种独立机器人任务。

**奥数解答评分：IMO-GradingBench。** 输入题目、候选解答、参考解答与评分指南，预测 0、1、6、7 中的分数；以和专家标签一致的准确率评价，训练、验证、测试各 100 个任务。这个领域先被保留，之后用来检验跨领域的改进能力迁移。

“保留领域”不代表迁移过去以后完全不准学习：在新领域启动改进循环时，仍使用该领域的训练反馈和验证选择，最终测试集保持隔离。

### 2. 模型、预算与统计口径

自修改与任务执行并不总用同一个模型。Appendix D.1 指定：编程自修改用 Claude 3.5 Sonnet（New）、任务执行用 o3-mini；论文评审自修改用 Claude 4.5 Sonnet、执行用 GPT-4o；机器人两者均用 Claude 4.5 Sonnet；奥数评分自修改用 Claude 4.5 Sonnet、执行用 o4-mini。

因此，本篇结果首先是**特定模型组合、工具与评估流程下的系统结果**，不是某一个基础模型在所有任务上的统一能力分数。

§5 说明每个实验中的方法重复运行 5 次，报告中位数，以及由 1,000 次 bootstrap 重采样得到的 95% 置信区间，并使用 Wilcoxon signed-rank test 检验显著性。下文用“CI”表示这些区间。**50 次修改不是 50 次独立实验**，同一演化轨迹里的子代相互依赖。

还有一个会影响读图的细节：多领域联合评估采用早停门槛。若候选在任一领域的初步评估中失败，两个领域都不会继续完整评估，剩余任务记为零。因此，零分不总等于系统在完整任务集上被逐项测过且全部答错。

### 3. 对照组怎样拆解贡献

- **DGM：** 使用原始、面向编程的固定指令生成机制。
- **DGM-custom：** 人工把指令生成机制适配到新领域。这是比直接照搬编程提示更强、更重要的对照。
- **DGM-H w/o self-improve：** 固定初始 meta agent，仍允许它改进 task agent。不是“什么都不许改”。
- **DGM-H w/o open-ended exploration：** 不保留候选档案，新版本替代前一版本，用来检验档案式探索的作用。
- **静态领域基线：** AI-Scientist-v2 reviewer、默认机器人奖励，以及数学评分中的 ProofAutoGrader。

### 4. 任务层结果，以及不能省略的限定

编程运行 80 轮后，DGM-H 在用于报告训练表现的 50 题子集上从 0.140 提升至 0.340，CI 为 0.300–0.380；在论文所称的完整 Polyglot benchmark 上从 0.084 提升至 0.267，CI 为 0.231–0.280。原始 DGM 的完整 benchmark 历史结果是 0.142→0.307。两者起点不同，论文将结果解释为可比的自改进能力，而非 DGM-H 全面胜出。

这里有一个数据口径提醒：主文称完整 Polyglot benchmark 包含“大部分未见任务”，附录 C.1 的措辞及 Table 2 又涉及 165 个未见/测试任务。本笔记保留主文的“完整 benchmark”称谓，不将 0.267 无条件改写成“纯未见 165 题的准确率”；精确复现实验还需核对公开划分。

评审与机器人联合实验运行 100 轮后：

- **评审：** DGM-H 的测试准确率为 0.710，CI 为 0.590–0.750；静态 AI-Scientist-v2 reviewer 为 0.630；DGM-custom 为 0.590，CI 为 0.570–0.650。
- **机器人：** DGM-H 的测试任务分数为 0.372，CI 为 0.355–0.436；默认奖励基线为 0.348；DGM-custom 为 0.348，CI 为 0.305–0.385。
- **冻结 meta agent：** 两个领域分别为 0.0 和 0.213；移除档案后分别为 0.0 和 0.116。论文报告完整 DGM-H 相对这两项消融的差异显著。

**但 DGM-H 与 DGM-custom 的差异在两个领域都不显著，$p>0.05$。** 因而合理的说法是：它自动形成了有竞争力的改进流程；不能写成“已显著超越人工定制流程”。

另一个尤其重要的限定：初始评审 agent 得分为零，原因包括缺少任务所需的输出格式与解析后处理。**从零到 0.710 不等于基础模型的评审知识从零被创造出来。** 改好输出协议本身有工程价值，但若要研究更深层的改进能力，就应进一步采用格式已经正确、功能已经可用的起点。

## 五、核心指标：如何测量“改进能力变强”

### 1. improvement@k 测的不是成功次数

§5.2 提出 improvement@k，简称 `imp@k`。它问的是：

> 给定起始 task agent、一个固定的 meta agent，以及固定的生成流程，让它最多生成 $k$ 个修改版本，最终能带来多大的任务性能提升？

Appendix D.3 的形式化定义可写成：

$$
\operatorname{imp@}k(M,A,G,T)
= \max_{A'\in\mathcal{A}^{(k)}(M,A,G)}
\operatorname{Evaluate}(A',T)
-\operatorname{Evaluate}(A,T)
$$

其中 $M$ 是固定改进器，$A$ 是初始任务 agent，$G$ 是生成与搜索算法，$T$ 是评估任务，$\mathcal{A}^{(k)}$ 是最多 $k$ 步中生成的候选集合。

注意它是**任务分数的差值**，不是 pass@k，也不是“前 k 次修改中有几次成功”的比例。若任务指标是准确率，`imp@50 = 0.20` 表示提高了 20 个百分点，不是相对提高 20%，也不是 50 次尝试中成功了 20%。

### 2. 必须区分验证选择和测试报告

附录公式把“取最好”的细节压缩了。正文 §5.2 明确说：按 validation score 选择最佳生成版本，再报告 test performance。为便于设计实验，可以把这一流程展开成下面的写法；这是本笔记对数据划分的显式表达，不是额外宣称论文提出了一个新公式：

$$
A^* = \underset{A'\in\mathcal{A}^{(k)}}{\arg\max}\; Q_{\mathrm{val}}(A'),
\qquad
\operatorname{imp@}k = Q_{\mathrm{test}}(A^*)-Q_{\mathrm{test}}(A).
$$

训练反馈用于产生改动，验证集用于挑选候选，测试集用于最终报告。**不能看过所有候选的测试分数，再挑测试集最高的那个。** 否则测试集已经变成搜索反馈。

一个虚构的计算例子：同一个起点测试准确率为 0.40，旧改进器在 50 次修改后选出的版本为 0.52，新改进器为 0.61，则各自的 `imp@50` 为 0.12 与 0.21。这个例子只是解释指标，不是论文结果；实际还要比较多次独立运行及不确定性。

### 3. 为什么诊断时反而要冻结改进器

如果测量期间允许 $M$ 不断变化，就很难回答“这个具体版本的改进器有多好”。它既在改题目解法，也在继续学习如何改进，两个过程混在一起。

所以 §5.2 **先从演化结果中拿出一个改进器，再固定它，测它产生任务改进的能力**。冻结的是接受测量的对象，不是说整个研究不做 meta 层的演化。

这可以类比为：教练先学习新的训练方法，之后在测试中固定这套方法，看它能把学员带到什么水平。教练自己在测试期间又不断换方法，就难以判断起始方法的效果。

### 4. 跨领域迁移：Figure 3 应该怎样读

作者先在论文评审与机器人奖励设计上演化系统，再迁移到此前保留的奥数评分领域。所有 §5.2 实验都运行 50 次修改，且固定接受测量的 meta agent。

![Hyperagents 的改进能力迁移实验：冻结改进器后，迁移版本在奥数评分任务上获得更大的 improvement@50](./img/hyperagents-fig03-improvement-at-50.png)

*图 2：原论文 Figure 3，PDF 第 10 页。左侧是训练任务表现随修改次数的变化；中、右侧比较起点与生成版本的测试表现。迁移 DGM-H 的 imp@50 中位数为 0.630。来源：原 PDF，CC BY 4.0，裁切保留全部坐标与图例。*

关键结果是：

- 使用初始 meta agent，DGM 的 `imp@50` 为 0.0，CI 为 0.0–0.0；DGM-H 为 0.0，CI 为 0.0–0.130。
- 从先前 DGM-custom 实验迁移的版本，`imp@50` 仍为 0.0，CI 为 0.0–0.010。
- 从先前 DGM-H 实验迁移的版本，`imp@50` 达到 **0.630**，CI 为 **0.540–0.630**。

这支持“源领域演化出的系统带来了可迁移的改进能力”，而不只是“它在源领域记住了更好的答案”。

不过，需要保留两个重要限定：

**第一，迁移的是整个 hyperagent，包括 task agent 和 meta agent。** 迁移前后在新领域的起始得分都接近零，不代表起始任务程序逐字相同。因此，它不是一个严格的“锁死同一个任务程序、只交换 meta agent”的因果实验。若希望把效果进一步归因到改进器本身，可以增加这种更严格的交换对照。

**第二，迁移版本并非简单取源领域分数最高者。** Appendix D.4 根据一个节点后代相对该节点的平均增益，并按谱系距离折扣来选择“更好的垫脚石”；折扣因子为 0.6，候选至少有 3 个后代。这是一种启发式代理：容易产生好后代值得关注，但不等于已无偏估计其改进能力。

### 5. improvement@k 仍然不是完整答案

相同 $k$ 只对齐修改次数，不保证模型调用量、生成长度、执行时间或模拟器成本相同。一个改进器每轮调用十次模型，另一个只调用一次，即使都是 50 轮，也不是同等成本。

此外，绝对增益受起点影响：准确率 0.70→0.80 往往比 0.00→0.10 更难，Appendix D.3 也明确讨论了饱和效应。实际比较应尽可能对齐初始程序、任务难度、生成流程和费用，并同时报告起始分数与最终分数，而不是只展示一个差值。

## 六、继续自我修改：有没有证据表明收益会累积

### 1. 这是另一组实验，不要和冻结测量混在一起

§5.3 不再固定改进器，而是让迁移后的 DGM-H 在奥数评分领域继续修改自己，运行 200 轮，观察已有改进机制能否被复用并继续产生收益。

![迁移后继续自修改的结果：从初始系统、迁移系统与 ProofAutoGrader 强起点出发的训练曲线及测试分数](./img/hyperagents-fig04-compounding.png)

*图 3：原论文 Figure 4，PDF 第 13 页。蓝色为初始 DGM-H，橙色为迁移 DGM-H，绿色将迁移改进器与 ProofAutoGrader 任务程序结合。来源：原 PDF，CC BY 4.0。蓝、橙测试中位数分别为 0.610、0.640，论文报告差异不显著。*

结果可以拆成两层理解：

1. **初始版本与迁移版本比较。** 初始 DGM-H 最终测试分数为 0.610，CI 为 0.510–0.680；迁移版本为 0.640，CI 为 0.550–0.720。迁移版本中位数更高，但差异不显著，$p>0.05$。
2. **从更强任务程序起步。** 将 ProofAutoGrader 作为 task agent，并接入迁移 meta agent，最终在该实验测试子集上达到 0.700，静态 ProofAutoGrader 为 0.670。

作者还在完整 IMO-GradingBench 上评估第二组的最佳版本：准确率由 0.561 提升至 0.601，平均绝对误差由 0.178 降至 0.175。**这里是另一个评估范围，不能把子集的 0.700 和全量的 0.601 混在同一条性能提升叙述中。**

### 2. 合理结论与过度解读

合理的结论是：已有演化结果可复用；系统能够在更强的任务程序上继续找到改进；进一步累积收益是值得研究的方向。

但这些有限轮数、有限任务的结果还不能证明“递归能力必然越来越强”“长期加速已经成立”或“能够无上限自我提升”。特别是 0.640 与 0.610 的比较，应把不显著结果和均值／中位数一起讲清楚，而不是只展示看起来更高的柱子。

## 七、局限与开放问题：读完应该保留哪些怀疑

### 1. 任务分布和外层规则仍是固定的

论文 §7 明确指出固定任务分布、父代选择和评价协议限制了无界进展。系统没有在主实验中同时发明全新的任务空间与独立有效的衡量标准。

### 2. 低起点和格式修复可能放大视觉上的进步

初始程序缺少任务专用解析，导致评审和奥数评分得分为零。这样的起点便于展示系统自动搭建流程的能力，但要研究“更聪明的改进策略”，最好补充格式有效、工具完整、表现不弱的起点。ProofAutoGrader 初始化实验朝这个方向迈了一步。

### 3. 运行次数与跨任务外推仍然有限

5 次独立运行能够揭示部分随机性，但不能把 100 或 200 个连续子代当成同样数量的独立样本。要判断跨算子、跨架构或跨硬件迁移，还需要独立任务来源及对应的统计设计，不能仅靠同一来源下增加形状数量。

### 4. 迁移收益必须和获得迁移版本的成本一起看

“到新领域后很快改好”可能建立在昂贵的源领域搜索之上。实际应用至少需要区分新任务上的增量成本，以及包含源领域演化成本的总成本。

Appendix D.2 给了 token 估算，但还有一个应谨慎引用的细节：它列出 100 轮自修改约 33M tokens，每轮评估约 0.506M tokens，同时写总计 88.6M。按这些分项直接相加是 $33+0.506\times100=83.6$M，和正文总数不一致。这里不推断缺失了什么费用；复现预算应依据日志重新核算，而非把估算当成确定账单。

### 5. 机制解释和安全约束需要独立证据

记忆、错误归纳和性能追踪是有吸引力的解释，但还需定向消融。允许修改自身也要求隔离评估器、测试数据、凭据与资源权限；“跑在沙箱里”不是对任何未来自修改系统的普遍安全保证。

## 八、个人思考：它给 AProf 的启发是什么

> 本节是将论文思想映射到技能演化项目的个人分析，不是 Hyperagents 的实验结论，也不是 AProf 已经完成的结果。

### 1. 不要直接把 kernel 加速叫作 RSI

可以把观察对象分成三层：

- **任务层：** 某次优化产出的 kernel 是否正确、是否更快。
- **技能层：** 技能库改变以后，同一个执行模型是否能在未参与编辑的任务上做得更好。
- **改进器层：** 负责选择经验、解释失败和编辑技能的方法，是否能在相同起点与预算下产生更好的技能库。

第三层最接近这篇论文希望单独测量的东西。于是研究问题可以先收窄为：**“从硬件反馈中演化出来的技能改进器，能否更高效地改进新任务上的技能库？”** 这比一开始就宣称整个系统具备通用 RSI 更容易形成可检验的论文主张。

### 2. 一个比直接照搬迁移更严格的检验

借鉴冻结 meta agent 的诊断思路，可以让旧、新改进器分别从同一个初始技能库出发，保持执行模型、工具权限、候选动作和外层预算一致；在开发数据上编辑并选择最终库，然后锁定版本，在未见 operator/source groups 上比较。

如果新改进器的优势来自人工重新写提示，这首先是人工方法改进；若要研究自我改进，需要保留“系统自动产生新改进方法，并由该方法驱动后续修改”的版本与调用证据。

“只交换改进器”的严格对照尤其有价值，因为它排除了起始技能库也一起变强的解释。还应比较固定改进器、简单规则和直接等预算搜索，防止把多花算力产生的效果误归因于 meta 层演化。

### 3. 硬件任务有更客观的反馈，但也有新的难点

论文评审依赖历史录用标签；kernel 优化则可以使用正确性和真实耗时，反馈更容易落到可执行测量上。不过，计时噪声、编译成本、profiling 开销和不同平台的资源差异，都让“相同轮数”更加不足以代表公平预算。

任务分数可考虑“在固定求解预算内，正确且稳定超过预定加速阈值的任务比例”，同时报告失败、回退、回归与实际费用。再用新旧技能库在这一任务分数上的差值衡量技能收益，用固定预算内改进器能产生的技能收益比较改进能力。

这里不急着把速度、token 和设备时间拼成带任意权重的总分。阈值应依据噪声和实际意义预先确定；独立测试应按任务来源隔离，而不是在同一算子附近换几个形状就宣称泛化。

对于跨硬件迁移，更有希望迁移的是“怎样判断瓶颈、组织实验、排除错误经验”的方法，而非原封不动搬运某个 tile 参数。**这是可检验的研究假设，不是本篇论文已证明的跨硬件结论。**

### 4. 我最想继续讨论的问题

如果一个系统能够保留有效的优化经验，但不会改变自己总结经验和选择修改的方式，它已经是有价值的技能学习系统；我们是否真的需要让改进器本身演化？

这个问题应先由对照实验回答。只有固定改进器显现出稳定、可复现的瓶颈，而新改进器能在公平条件下突破它时，增加递归层次才有明确的研究价值。

## 九、结论

Hyperagents 最适合作为 RSI 入门第一篇的原因，不是它给出了一个“会自己无限变强”的完成品，而是它让研究问题变得可以拆解：

1. **实现上，** task agent 和 meta agent 都可以修改，但外层评价仍须清楚划界。
2. **实验上，** 任务能力与改进能力需要分别测量；冻结改进器的 `imp@k` 是一个实用起点。
3. **论证上，** 跨领域迁移提供了积极证据，但起点差异、费用、统计显著性和有限任务范围都不能省略。

对技能演化项目而言，先证明“在相同起点和预算下，自动产生的新改进方法更有效”，比先追求一个很大的 RSI 叙事更有说服力。
