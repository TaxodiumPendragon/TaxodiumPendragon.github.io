## 1.

概念：
- 语句覆盖要求设计一组测试用例，使得被测程序中的每条可执行语句都至少被执行一次。其缺陷在于，对显式存在的语句可以实现完全覆盖，但无法覆盖隐式的分支。
- 分支覆盖着重关注程序中的分支结构，以尽可能地覆盖程序中判定地每个 true 分支和 false分支。
- 条件组合覆盖要求设计足够的测试用例，使每个判定中所有的条件取值组合至少执行一次。如果遵循这一规定，我们说就实现了条件组合覆盖。
- 路径覆盖要求执行所有可能的穿过程序的控制流路径

其中，语句覆盖是最弱的逻辑覆盖准则，可能无法发现判断中逻辑运算符出现的错误；分支覆盖比语句覆盖稍强，但它也未必能发现每个条件的错误；条件组合覆盖比分支覆盖更强，只要满足了条件组合覆盖就一定满足分支覆盖；路径覆盖是最强的，但一般是不可实现的。

## 2.软件测试步骤及其作用

软件测试的步骤：
1. 单元测试（往往采用白盒测试技术）：集中于每个独立的模块。该测试以详细设计文档为指导，测试模块内的重要控制路径。
2. 集成测试：集中于模块的组装。其目标是发现与接口有关的错误，将经过单元测试的模块构成一个满足设计要求的软件结构。
3. 确认测试（有效性测试）：目标是发现软件实现的功能与需求规格说明书不一致的错误。（通常采用黑盒测试技术）
4. 系统测试：集中检验系统所有元素（包括硬件、软件）之间协作是否合适，整个系统的性能、功能是否达到。

##  3基于流程图的测试模型建立与条件组合覆盖设计

### 测试模型

根据题目给出的流程图，可将程序抽象为如下**判定—处理结构模型**（循环视为一个整体过程块）：

#### 1. 输入变量
- x, y：程序初始输入

#### 2. 判定与处理逻辑（按执行顺序）

1. **判定 D1**：`x ≥ 0 ∧ y ≥ 0`
   - T 分支：执行 `S2`（不改变 x、y）
   - F 分支：执行  
     ```
     x := x * x
     y := y * y
     ```

2. **初始化**  
s := 0

3. **循环判定 D2**：`s > x`
- F：执行 `s := s + y`，回到 D2
- T：退出循环  
> 按题意：循环结构整体视为一个过程块

4. **判定 D3**：`s < y * y`
- T 分支：执行 `S4`
- F 分支：执行 `S3`

#### 3、条件组合覆盖分析

 1. 判定 D1 的基本条件
- C1：`x ≥ 0`
- C2：`y ≥ 0`

需覆盖 **所有可行的条件组合**：

| 编号 | C1 | C2 | 判定结果 |
|----|----|----|----|
| D1-1 | T | T | T |
| D1-2 | T | F | F |
| D1-3 | F | T | F |
| D1-4 | F | F | F |

 2. 判定 D2（循环判定）

- 条件：`s > x`
- 需覆盖：
- 第一次判断为 F（进入循环）
- 某次判断为 T（退出循环）

 3. 判定 D3 的条件

- 条件：`s < y * y`
- 需覆盖：
- T
- F

## 4伪代码

给定程序的功能可概括为：

- 输入：`price`（单价）、`quantity`（数量）、`isVip`（是否 VIP）
- 若输入非法（price < 0 或 quantity < 0），输出错误信息
- 否则计算总价 `total = price * quantity`
- 根据是否 VIP 以及 total 的大小，应用不同折扣规则
- 最终输出 total

### 测试模型

从软件工程中白盒测试角度，将程序抽象为如下判定—执行模型：

### 1. 判定节点

| 编号 | 判定条件 |
|----|----|
| D1 | price < 0 OR quantity < 0 |
| D2 | isVip > 0 |
| D3 | total > 200 （VIP 分支） |
| D4 | total > 100 （非 VIP 分支） |

### 2. 控制流结构

```text
↓
D1: price < 0 OR quantity < 0 ?
├─ T → 输出错误信息 → 结束
└─ F → total := price * quantity
↓
D2: isVip > 0 ?
├─ T → D3: total > 200 ?
│ ├─ T → total *= 0.8
│ └─ F → total *= 0.9
└─ F → D4: total > 100 ?
├─ T → total *= 0.95
└─ F → 不打折
↓
输出 total
结束
```

---

### 分支覆盖

需要覆盖的分支包括：

| 判定 | 需要覆盖的分支 |
|----|----|
| D1 | T / F |
| D2 | T / F |
| D3 | T / F |
| D4 | T / F |

## 一、命名与可读性问题

### 1. 变量命名不规范
- 问题：
  - 使用拼音变量名 `zhongjian`
  - 参数名 `numsVec` 与实际使用的 `nums` 不一致
- 影响：
  - 降低代码可读性与可维护性
- 修改建议：英文命名
  ```cpp
  int mid = left + (right - left) / 2;
  ```

### 2. 变量名使用错误

形参是 `numsVec`，但代码中使用了 `nums`

会使得代码无法编译

修改建议：

```cpp
int right = numsVec.size() - 1;
if (numsVec[mid] == target_num)
```
### 3. size() 与 int 混用

`numsVec.size()` 返回 `size_t`，直接赋值给 `int`，可能导致隐式类型转换问题

修改建议：

```cpp
int right = static_cast<int>(numsVec.size()) - 1;
```

或统一使用 size_t

### 4. if-else 缩进与花括号不统一

else if 分支未使用花括号，易引发维护错误

修改建议：
```cpp
else if (numsVec[mid] < target_num) {
    left = mid + 1;
}
```

### 5使用 -2 表示“未找到”

接口语义不清晰，调用者易误用

修改建议：

使用 -1或 std::optional<int>

```cpp
return -1;
```
