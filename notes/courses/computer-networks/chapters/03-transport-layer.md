## 1.传输层基本概念

>套接字、端口号、★复用与分用

- 套接字（socket），是应用层和传输层的接口，也是应用程序和网络之间的API
- 端口号：套接字标识的一部分：
- - 每个套接字在本地关联一个端口号
- - 端口号是一个16比特的数
- - 分为熟知端口、注册端口、动态或私有端口
- - 在报文段携带，源端口 目的端口号



- (发送端)**复用**：传输层从多个套接字收集数据，交给网络层发送。
> 简单来说是把多个应用层东西用相同的路传输出去
- (接收端)**分用**：传输层从网络层接受数据，交付正确的套接字

## 2.	UDP

网络层提供的服务（best-effort service）：
- 尽最大努力将数据包交付到目的主机
- 不保证投递的可靠性和顺序
- 不保证带宽及延迟要求

### UDP提供的服务

- 对网络层接口进行最简单的封装：网络层 + 多路复用与分解
- - 将主机-主机的数据交付 -> 进程-进程的数据交付
- - 报文完整性检查（可选）：检测并丢弃出错的报文
- UDP的实现：
- - 复用和分用（必须）
- - 报文检错（可选）checksum不用就填0


### UDP报文
- 报头：携带协议处理需要的信息
- 载荷（payload）：携带上层数据
用于复用和分用的字段：
- 源端口号
- 目的端口号
用于检测报文错误的字段：
- 报文总长度
- 校验和（checksum）：要包括伪头、UDP头和数据三个部分，UDP伪头信息取自IP报头，为了避免IP地址错误投递，包括：
- - 源IP地址，目的IP地址
- - UDP的协议号
- - UDP报文段总长度

缓冲区
- 通常端系统实现（如Linux）：无发送缓冲区、有接收缓冲区
- 发送方：从应用层获取的数据，传输层加上UDP头部后直接交给网络层
- - 长消息的分片、缓冲依赖于网络层、链路层提供
- 接收方：每个socket一个缓冲区，存储着来自不同发送方的报文

应用：流媒体、单次响应请求如DNS，要可靠找应用层

## 3.★一般性可靠传输及其性能优化

- rdt1.0:乌托邦协议：有就发，收到就解传
- 信道有差错但不丢包
- - rdt2.0：ARQ自动重传，有错NAK，没错ACK；停等式
- - rdt2.1(ACK也会错)：加上序号，忽略重复序号；
- - rdt2.2：不要NAK,ACK加一个上个收到的seq，重传：出错或ACK.seq != seq
- rdt3.0：信道有差错且丢包
- - 超时重传

性能优化：

### 回退N

发送方状态机那里不需要检验返回的会不会大于base，根本逻辑是如果乱序的话接收方根本不会发ACK

回退N协议（GBN）：发送方窗口大小 \(N\) 必须满足 \(N \le M-1\)（序列号空间大小为 \(M\)）。
> 证明：反正若N=M,同样考虑ACK全丢的情况,旧窗口为 \([0,\,M-1]\)，新窗口为 \([M,\,2M-1] \pmod{M} = [0,\,M-1]\)，两窗口完全重叠，无法区分新旧包。

序列号减一

### 选择重传

- 重点在于接收方要对更古老一个窗口的包重新确认发ACK来辅助发送方窗口更新
- 窗口大小不能超过seq取值空间的一半。更好的说法：seq范围必须是窗口大小两倍
- 序列号两倍
> 证明：假设窗口大小为 \(N\)，序列号空间大小为 \(M\)（模 \(M\)）。在 ACK 全部丢失的最坏情况下，旧窗口为 \([0,\,N-1]\)，新窗口为 \([N,\,2N-1] \pmod{M}\)。为避免混淆，需要保证 \(0\) 不落入新窗口：
> \[
> 0 \notin [N,\,2N-1] \pmod{M}.
> \]
> 若上界越过 \(M-1\)，则区间回绕并包含 0：
> \[
> 2N - 1 \ge M \;\Rightarrow\; [N,\,2N-1] \pmod{M} \text{ 覆盖 0}.
> \]
> 因此必须有：
> \[
> 2N - 1 < M \;\Rightarrow\; 2N \le M \;\Rightarrow\; N \le \frac{M}{2}.
> \]
> 结论：窗口大小需满足 \(N \le \tfrac{M}{2}\)，即可避免旧、新窗口在模空间重叠。



## 4.	★TCP可靠传输

- 基本机制：流水线传输
- - 发送端：流水线式发送数据、等待确认、超时重传
- - 接收端：进行差错检测、确认接收
- 对字节建立序号，而非报文
- - ACK值为下一个期望的字节序号，而非当前已经收到的最后一个字节
- - ACK值放在正常数据包里（捎带，piggyback）
- 虽然没规定但是通常会缓存

**发送方**：
- 定时器的使用：仅对最早未确认的报文段使用一个重传定时器（与GBN类似）
- 重发策略：仅在超时后重发最早未确认的报文段（与SR类似，因为接收端缓存了失序的报文段）

**接收方**：
- 确认方式：采用累积确认，仅在正确、按序收到报文段后，更新确认序号；其余情况，重复前一次的确认序号（与GBN类似）
- 失序报文段处理：缓存失序的报文段（与SR类似）

### 应用
- 发现ACK虽然没收到，但是如果能收到后面的ACK就说明之前的包已经收到了，可以直接更新窗口，不用等超时重传。避免了额外重传

TCP通过采用以下机制减少了不必要的重传：
- 只使用一个定时器且只重发第一个未确认报文，避免了超时设置过小时重发大量报文段
- 利用流水式发送和累积确认，可以避免重发某些丢失了ACK的报文段

### 超时值优化

超时值设置：一般大于RTT
- 平均RTT的估算方法（指数加权移动平均）：
$EstimatedRTT = (1- \alpha)*EstimatedRTT + \alpha*SampleRTT
典型地，\alpha = 0.125$

估算SampleRTT 与 EstimatedRTT的偏差（称DevRTT）：
$DevRTT = (1-\beta)*DevRTT + \beta*|SampleRTT-EstimatedRTT|$
典型地， $\beta = 0.25$
设置重传定时器的超时值：
$TimeoutInterval = EstimatedRTT + 4*DevRTT$

TCP二义性影响测量sampleRTT解决方法：
- 忽略有二义性的确认，只对一次发送成功的报文段测量SampleRTT ，并更新EstimtedRTT
- 当TCP重传一个段时，停止测量SampleRTT

Karn算法结合使用RTT估计值和定时器补偿策略确定超时值：
- 使用EstimatedRTT估计初始的超时值
- 若发生超时，每次重传时对定时器进行补偿（超时值加倍，至一个上限），直到成功传输一个报文段为止
- 若收到上层应用数据、或某个报文段没有重传就被确认了，用最近的EstimatedRTT估计超时值

### 优化2：快速重传

TCP协议规定：
当发送方收到对同一序号的3次重复确认时，立即重发包含该序号的报文段

### 接收端

推迟确认
- 接收端收到若干报文段后发送累计确认的报文段
- TCP协议规定：
- - 推迟确认的时间最多为500ms
- - 接收方至少每隔一个报文段使用正常方式进行确认
- - 也就是收到一个期待报文段且之前报文段都发送过确认才进行推迟（如果前一个被推迟、收到的失序报文-报文段有空隙、收到的是填充间隙）

## 7.TCP流量控制：非零窗口、糊涂窗口

- 接收缓存：避免接收端缓存溢出丢失。进行流量控制发送端TCP调节发送速率不让其溢出 
- 非零窗口：发送零窗口通告，接收方启动零窗口探测（启动一个定时器，如果超时就发送一个零窗口探测）
- 发送方/接收方对零窗口的处理：
- - 发送方：当接收窗口为0时，发送方必须停止发送
- - 接收方：当接收窗口变为非0时，接收方应通告增大的接收窗口

- 糊涂窗口综合征：当数据的发送速度很快、而消费速度很慢时，零窗口探测的简单实现带来以下问题：
- - 接收方不断发送微小窗口通告
- - 发送方不断发送很小的数据分组
- - 大量带宽被浪费

启发式接收方策略解决
- Clark策略：窗口显著增加后才发送更新的窗口通告。显著增加为当前窗口大小是存储空间一般或者一个MSS，取min
- 与推迟确认结合：推迟发送ACK

发送方策略
- Nagle算法
- - 在新建连接上，当应用数据到来时，组成一个TCP段发送（那怕只有一个字节）
- - 如果有未确认数据，后续到来的数据放在发送缓存中
- - 当（1）数据量达到一个MSS且窗口大小大于等于MSS，或（2）收到所有已发数据的确认
- - 用一个TCP段将缓存的字节全部发走
- - 优点：综合考量，缺点：增加延迟

## 8.	★TCP拥塞控制：慢启动、拥塞避免、快速恢复、Tahoe算法与Reno算法区别、AIMD吞吐量与公平性

> 流量控制与拥塞控制的异同：
- 流量控制：限制发送速度，使不超过接收端的处理能力
- 拥塞控制：限制发送速度，使不超过网络的处理能力

网络拥塞造成丢包(路由缓存满)分组延迟增大，使得大量网络资源重传和转发

### 常用方法
- 网络内部的拥塞控制：路由器/交换机向端系统显式反馈，现代TCP变种ECN会用来控制
- 端到端拥塞控制：传统TCP，自行观察丢包和延迟

慢启动

拥塞避免

Tahoe和Reno区别是Tahoe在超时或者重复ACK时都进入慢启动，而Reno在重复ACK时进入**快速恢复**

## 9.新型传输层技术

>BIC与CUBIC：算法基本思想

### BIC二分查找

> TCP经典拥塞控制：当端到端时延带宽乘积（BDP）较大时，拥塞窗口增长过慢，导致信道无法满载

思想
- 如果丢包，窗口大小W，初始化Wmax=W，说明实际窗口最大值应该在W以下
- 丢包后W/2,初始化Wmin=W/2，若成功收到ACK，说明实际窗口最大值应该在W/2以上


ACK驱动的查找
- 每经过一个RTT，若无丢包发生，便将窗口设置到Wmax和Wmin的中点，一直持续到接近Wmax
- 更新Wmin


```cpp
while (Wmin <= Wmax) { 
    inc = (Wmin+Wmax)/2 - cwnd;
    if (inc > Smax)
             inc = Smax;
    else if (inc < Smin)
             inc = Smin;
    cwnd = cwnd + inc * MSS / cwnd;
    if (no packet losses)
             Wmin = cwnd;
    else
             break;
}
```
不公平性：RTT较小的连接增长更快

### CUBIC

核心思想：
- 窗口增长函数仅仅取决于当前距离上次丢包经过的时间t
- 从而，窗口增长完全独立于网络的时延RTT
CUBIC的RTT独立性质使得CUBIC能够在多条共享瓶颈链路的TCP连接之间保持良好的RTT公平性
- 使用三次函数来拟合
$W(t)=C(t-K)^3+W_{max}$
$W_{min}=\beta W_{max}$
- 其中，C为调整因子，K=$\sqrt[3]{\frac{W_{max}\beta}{C}}$,区间宽度不依赖ACK，区间其实时刻为最近一次检测丢包时间


>(不考)TCP Vegas:基本思想线性预测吞吐量，线性增加减少cwnd。重传改进：计算出来的RTT大于timeout的时候直接重传
>TCP Westwood:主要用于无线网络，检测ACK到达速率进行带宽估计

### BBR

> 算法优化目标（与传统TCP的差异），算法过程不要求

- 要测量最大带宽，就要把瓶颈链路填满，此时buffer中存在排队分组，延迟较高
- 要测量最低延迟，就要保证链路队列为空，网络中分组越少越好，cwnd较小

瓶颈链路BDP，其带宽为BtlBw

传统TCP拥塞控制
- 以丢包事件为驱动，探测阶段将瓶颈链路上的缓冲区填满直至丢包，并以此为依据判断是否进行被动的乘性减小
- 目标：认为BDP + BtlneckBufSize是最优窗口大小
BBR
- 目标：认为BDP是最优窗口大小
- 相比于传统TCP，BBR的目标更有优势
- - 相同的吞吐量
- - 更低的延迟、更小的丢包风险
- 核心思想：获知当前BDP，将cwnd往BDP调整

过程：瓶颈带宽探测、时延探测

### DCTCP

> 发送端、接收端、交换机各自任务（发送端计算公式不要求，如考到题目中会给出）

针对数据中心的TCP

背景特点
- Incast问题：大量短连接同时发送数据，导致交换机缓存溢出丢包
- Queue buildup问题：长连接持续发送数据，导致交换机缓存积压，增加短流时延
- Buffer Pressure

要容忍高突发流量、低时延和高吞吐，因此传输层协议将缓冲区队列长度维持在一个较低水平

### QUIC：网络体系架构与优势，实现方式不要求


基于QUIC的传输架构
- QUIC替代TCP、TLS和部分HTTP的功能
QUIC实现在用户态中
- 底层基于UDP实现
- 拥塞控制是模块化的，可以方便地使用各种TCP拥塞控制算法，如CUBIC等

![QUIC架构](/assets/courses/computer-networks/notes/img03/QUIC.png)

优势
- 连接建立更快：1RTT连接建立，只需要三次握手，二传统TCP链接需要3RTT因为TCP内无法加入密钥

TCP多流复用时的队头阻塞问题
- TCP为保持数据的有序性，出现丢包时，会等待该数据到达后，再提交给上层应用
- 多流复用时，某个数据流的数据包丢失，会使得TCP连接上所有数据流都需要等待

QUIC对队头阻塞问题的解决
- 在单个连接中，建立相互独立的多个QUIC流，某个流的数据包丢失不影响其它流的数据交付
- 分析：TCP保证了整个连接的数据交付的有序性（有序）; QUIC利用了各个流相互独立的特性，仅保持了流内部数据的有序性（部分有序），减少了不必要的等待
- 同时限制：单个流对接收端缓冲区的占用不能超过阈值

明确的包序号和更
易于部署和更新
